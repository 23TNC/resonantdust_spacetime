# AGENTS.md — shard module

## Purpose
SpacetimeDB 2.1.0 server module (Rust → wasm32). Authoritative gameplay state: the world (`cards`, `zones`), the soul mirror (`souls`), the player roster (`players`, `player_profiles`, `lifecycle_pending`), and the recipe / movement pipelines. Publishes to `resonantdust-<env>-shard` (see [`spacetime.<env>.json`](spacetime.dev.json) — `--env <env>` to switch). Compiles and runs inside a Docker-hosted SpacetimeDB instance — never against a host `spacetime` CLI.

Chat is a **separate module** ([../chat/AGENTS.md](../chat/AGENTS.md)) with its own database, queue, and wasm; nothing in this module references it.

Lifecycle-pending cards (magnetic anchors AND on_create-style decay cards) share one mechanism: a `lifecycle:` block on the card def stamps `FLAG_LIFECYCLE_PENDING` at creation via definition-flag inheritance, populates a `lifecycle_pending` detail row, and waits for the client to submit the declared recipe via `propose_action`. The original [magnetic rewrite](../../../../docs/MAGNETIC_REWRITE.md) dissolved the server-driven `magnetic.rs` tick into this client-driven pipeline; the [lifecycle rewrite](../../../../docs/LIFECYCLE_REWRITE.md) generalises it to cover on_create decay as well (still in progress — Phase 1 rename complete).

## Build & iterate
- **Always** use `bin/st build shard` (or `bin/st build` to do every module). The wrapper runs [`content/gen-ids.py`](../../../../content/gen-ids.py), then `cargo build --release --target wasm32-unknown-unknown` inside the build container with workdir set to `/workspace/server/modules/shard`, then regenerates TS bindings into [`../../../../pixijs/src/server/spacetime/bindings/shard/`](../../../../pixijs/src/server/spacetime/bindings/shard/). Don't reach for `cargo`, host `spacetime`, or ad-hoc `docker compose run` — even for introspection.
- `bin/st publish shard` / `bin/st republish shard` push the wasm to the running `start` container. The CLI loads [`spacetime.json`](spacetime.json) (anchor file — empty but its existence pins the CLI in this directory) plus [`spacetime.<env>.json`](spacetime.dev.json) for db name / server. `bin/st sql shard ...`, `bin/st select shard ...`, `bin/st call shard <reducer>` for live queries. See [`bin/st`](../../../../bin/st) and [bin/AGENTS.md](../../../../bin/AGENTS.md).
- TS bindings are generated; private tables (no `public`) are skipped during codegen. `player_sessions`, `sequence_counter`, `card_id_counter`, `lifecycle_pending`, and `gc_schedule` are intentionally private.

## The `valid_at` pattern
`cards`, `zones`, `players`, and `souls` share one primary-key shape (chat's `chat_messages` uses the same shape independently in its own module):

```
valid_at: u64 = (time_ms: u48 << 16) | sequence: u16
```

- **`valid_at` is the primary key**; the row's logical id (`card_id` / `zone_id` / `player_id`, etc.) is a `#[index(btree)]` column on the row. Two rows for the same id form a *history* of versions ordered by `valid_at_time`.
- **Time is milliseconds**, not seconds. Every module uses a local `fn now_ms(ctx) -> u64` that converts `ctx.timestamp.to_micros_since_unix_epoch() / 1_000`. The u48 ms slot has ~8920 years of runway.
- **The sequence is the source of PK uniqueness across writes at the same millisecond.** [`sequence::next_sequence(ctx)`](src/sequence.rs) hands out a fresh `u16` per call. Without it, two writes to different cards landing in the same ms would collide; with it, the only collision case is "same id, same `time_ms`."
- **Same-(id, time_ms) writes** are explicitly purged before insert. `cards::write_at` calls `delete_at(ctx, card_id, time_ms)` so "last write at this (id, ms) wins" — without the purge, the global sequence would let two rows for the same card share a time_ms, breaking in-reducer accumulation patterns (e.g. `souls::apply_slot_delta` firing N times at one `now_ms`, which is exactly what `bootstrap`'s starter-pack add-loop does).
- **Future-stamped rows are first-class.** Recipe completions and movement step queues are stamped at a `valid_at_time > now`. `latest()` therefore filters `valid_at_time ≤ now_ms` (max-by-key among those) — it does NOT just take the deepest row. `cards::prior_at(ctx, card_id, time_ms)` is the parameterised form used by writers that want "the row current at the time we're writing." Zones (`set_tile_at`) and souls (`apply_slot_delta`) use the same discipline.
- **`latest()` and `prior_at()` are not interchangeable.** A caller that has stamped a future row should reach the new state via `prior_at(..., future_time)`, never `latest()`. `on_create::trigger` exists in part because of this — it reads the card at the *creation row's* `valid_at_time`, not at `now`.
- **No `#[unique]` on non-PK columns.** Cross-row uniqueness (e.g. unique player names) can't be enforced via `#[unique]` — every version row would collide. Use `#[index(btree)]` and check via `latest_by_*()` lookup in the reducer before insert. Reducers are serialized per-database, so lookup-then-insert is race-free.
- **`#[auto_inc]` only on the PK.** When the PK moved to `valid_at`, the original id columns became caller-supplied. Cards now get ids from `cards::next_card_id` (private `card_id_counter` single-row table — *not* `content/gen-ids.py`, which only allocates `def_id`s for the catalog); zones via `zones::next_zone_id`; players via `players::next_player_id` (scan-and-increment fallback).

Client mirror: [pixijs/src/server/data/packing.ts](../../../../pixijs/src/server/data/packing.ts) and [pixijs/src/server/data/ValidAtTable.ts](../../../../pixijs/src/server/data/ValidAtTable.ts). Same packed-key shape, same "select max `valid_at_time` ≤ buffered_now per id" semantics. Schema changes here ripple through bindings and require updates over there.

## The `flags` column
`Card.flags` is `u32` (wider than the populated bit range; will shrink once the registry stabilises). Bit positions are pinned by [`content/cards/flags.json`](../../../../content/cards/flags.json); individual modules copy in the bits they need as local consts (see e.g. `actions.rs`, `on_create.rs`). The notable structured fields:

- **Bit 0** — tombstone. The pre-migration `position_hold` flag lived here; now reserved.
- **Bits 3 / 5 / 7** — `drop_hold` / `slot_hold` / `dead`. `HOLD_FLAGS_MASK` in [action_completion.rs](src/action_completion.rs) is the recipe-completion clearing mask.
- **Bits 8..=10 — `progress_style` (3-bit field).** Encodes which progress bar style the client should render for this row's "next future event." `0` = none, `1` = LTR/CW, `2` = RTL/CCW; rest reserved. Set on the actor's completion row; cleared on with-holds rows so non-event rows don't render bars from inherited state. `pack_progress_style` / `PROGRESS_STYLE_MASK` live in [action_completion.rs](src/action_completion.rs).
- **Bit 11 — `force_position`.** "Server is asserting this row's `micro_zone` / `micro_location` verbatim." Replaces the older `micro_zone.local_q = 1` disagree-with-anything trick. Set on `propose_action`'s chain-stitch / with-holds writes; cleared at completion.
- **Bit 12 — `magnetic_hold`.** Stamped on every row of a card whose def declares `lifecycle_recipe_key` + `lifecycle_duration_ms` (via definition-flag inheritance in [`cards::create_at`](src/cards.rs)). Stays set until a recipe consumes/transforms the card. The `lifecycle_pending` detail row keyed by `card_id` carries the corresponding `expires_at_ms` for the block-check gate.
- **Bits 13–16 — dirty/preserve markers.** `position_dirty` (13) / `position_preserve` (14) / `data_dirty` (15) / `data_preserve` (16). The `*_dirty` bits are server-managed and auto-set by `cards::write_at`'s diff against `prev_latest`; never set them manually. The `*_preserve` bits are caller-set intent flags that the forward-propagation helpers (`scrub_or_repath_position_forward`, `propagate_flag_diff_forward`) respect as stop/skip conditions.
- **Bits 17–19 — `position_hold_count` (3-bit field).** Saturating ref-count of how many distinct holders (chain stitches, has-predicate matches) currently claim a position hold on this card. Readers asking "is this card position-held?" check `count > 0`. Mutated via `cards::acquire_position_hold` / `release_position_hold` (or the lower-level `increment_position_hold_count` / `decrement_position_hold_count` flag transforms — those callers must follow up with `propagate_position_hold_forward(..., delta)` to keep future rows in sync). The bit-by-bit forward-prop (`propagate_flag_diff_forward`) ignores this field via `BOOKKEEPING_FLAGS_MASK` so the two propagators can't fight.
- **Bit 20 — `is_owned_by_player` (`FLAG_OWNED_BY_PLAYER`).** Disambiguates `Card.owner_id`. SET → `owner_id` is a `player_id` (only valid on soul cards); CLEAR → `owner_id` is a `card_id` (the immediate container; `0 = WORLD_PLAYER_ID` = world). [`cards::owning_player`](src/cards.rs) walks `owner_id` until it hits a row carrying this bit and returns that row's `owner_id` as the player.

Definition-level flags inherit on `create` / `create_at` — see `definition_flag_mask` in [cards.rs](src/cards.rs). Don't OR them by hand at every call site.

## Surface bands
`Card.surface` and `Zone.surface` are `u8`, but the values are banded into ranges with different semantics. The constants live in [packed.rs](src/packed.rs):

| Band | Constant | Purpose |
| --- | --- | --- |
| `0` | (reserved) | Sentinel "absent." Don't write here. |
| `1` | `INVENTORY_LAYER` | A soul's inventory bucket. `macro_zone = soul.card_id`. No hex tile data. |
| `2..32` | (reserved) | Future personal / panel surfaces. |
| `32..63` | `POCKET_DIMENSION_LAYER = 32` | Reserved for pocket-dimension-style surfaces that *do* carry tile data. `actions::derive_synthetic_hex` uses `surface >= SYNTHETIC_HEX_MIN_SURFACE = 32` to admit synthetic-hex resolution. |
| `63` | `MINI_ZONE_LAYER` | Mini_zones — radius-3 hex disks overlaid on the world. `macro_zone = anchor.card_id`. Backed by a real `Zone` row; cards placed on the mini_zone follow the same address. |
| `64..` | `WORLD_LAYER = 64` | World tiles. `macro_zone = packed (zone_q, zone_r)`. Synthetic hexes come from the underlying `Zone.tile_row`; if a mini_zone covers the same hex, it occludes. |

`actions.rs` and `action_completion.rs` both define `WORLD_LAYER = 64` locally — they MUST agree. The split between "carries tile data" (`>= 32`) and "panel / inventory" (`< 32`) is also the gating for synthetic-hex derivation.

## Stacks: chains and the wire format
`micro_zone: u8` has **two interpretations**, gated by `(stacked_state, surface)`:

- **Stack layout** — `stacked_state == OnRoot` AND `surface < 64`: `[position: u5 | direction: u1 | stacked_state: u2]`. The card's position in the chain and its direction off the root.
- **Legacy layout** — every other case (`Free` / `Slot` / `OnHex` / world cards): `[q: u3 | r: u3 | stacked_state: u2]`. Local (q, r) within the macro zone.

`StackedState` (4 variants) lives in [packed.rs](src/packed.rs):

- **`Free`** — Loose. `micro_location` is encoded `(x, y)` for surface-local positioning; `micro_zone` upper 6 bits are the legacy `(q, r)`.
- **`Slot`** — Parent-pointer slot. `micro_location` is the **immediate parent's** card_id (which can itself be `Slot`, `OnRoot`, `Free`, or `OnHex`), NOT the root. Used by `propose_action` to stitch recipe slots above the actor — chain integrity follows the actor when the recipe doesn't pin to a root. Direction bit in `micro_zone` is stored explicitly even though it could be derived from the parent — saves a chain walk on every render.
- **`OnRoot`** — Stacked on a rect chain root. `micro_location` is the **root's** card_id (not the immediate parent). Chain order comes from `micro_zone.position`; chain direction (top vs bottom of root) comes from `micro_zone.direction`. Rect-chain layout — this is the form `equip_card` and `propose_action` produce.
- **`OnHex`** — Stacked on a hex tile. `micro_location` is the parent hex card_id; walk via `micro_location` to find the root hex (which is `Free` on the world surface). Hex chains aren't migrated to the (root_id, position) model. Rect-on-hex (a rect card with state `OnHex`) is a leaf — no rect chain hangs off it.

The wire-format `CardStack` struct in [stacks.rs](src/stacks.rs) is a reducer-arg shape (not a table — uses `#[derive(SpacetimeType)]` instead of `#[table]`). `apply()` writes a stack's positioning into the cards table; `submit_action` (the original consumer) is currently commented out, so `apply` is only reachable through internal callers today. The client will see `CardStack` in generated bindings once any public reducer takes it again.

`unpack_micro_zone(micro_zone) -> (q, r, state)` and `pack_stack_micro_zone(position, direction, state)` / `pack_slot_micro_zone(direction)` / `pack_micro_zone(q, r, state)` switch between the two interpretations. Use the right packer for the state you're writing.

## Action pipeline
The recipe / action machinery spans three modules. Trace order:

1. **Trigger.** A new card is created (`utilities::add_card`, `character_creation::create_character`, or a product spawn inside `action_completion::apply`) and [`on_create::trigger`](src/on_create.rs) runs. It loads the card at its `valid_at_time` (via `prior_at`, since a future-stamped product isn't visible to `latest`), ranks all `OnCreate` recipes by `(hex_spec, root_spec, has_spec)`, and picks the best. If matched, `action_completion::apply` is called with `completion_ms = card.valid_at_time + duration`.
2. **Propose.** Client-driven actions enter via [`actions::propose_action`](src/actions.rs). It validates the proposed stack (existence, slot-hold guard, zone agreement), derives a synthetic hex from the zone tile if the client passed `hex = 0`, validates the lifecycle-id linkage for `Magnetic(_)` recipes, runs the [block-check gate](#lifecycle-resolution-gate) against the caller's `lifecycle_pending` rows, stamps `slot_hold` + `position_hold_count` + `force_position` on the participants at `now_ms`, then schedules the resolution by calling `action_completion::apply` with future `completion_ms`.
3. **Apply.** [`action_completion::apply`](src/action_completion.rs) writes the recipe outcomes as future-stamped rows at `completion_ms`: reagent rows flip `FLAG_DEAD`, products are spawned via `cards::create_at` (and their own `on_create::trigger` fires for any nested recipes), holds clear, synthetic-hex tiles revert to the underlying biome byte via `world_gen::biome_for`. The `souls::on_card_write` hook runs on every write, keeping the `souls` mirror table in sync with stat-bearing cards' lifecycle. Lifecycle-pending cards consumed here have their `lifecycle_pending` row removed by the dead-transition hook in `cards::write_at`.

The `actions` flow has no server-side action table — its state is the cards it stamped. The `lifecycle_pending` table tracks ACTIVE lifecycle-pending cards (one row per lifecycle-flagged card); see the next section.

## Lifecycle resolution gate
Lifecycle-pending cards (magnetic anchors today; on_create-style decay cards under the [lifecycle rewrite](../../../../docs/LIFECYCLE_REWRITE.md)) are recipes with a time-windowed phase. Resolution is **client-driven** — the server stamps initial state, the client decides when to submit success / failure / decay recipes via `propose_action`.

State on the server:
- [`lifecycle_pending`](src/lifecycle_pending.rs) — private table, one row per active lifecycle entry. Populated by `cards::write_at` when a card carrying `FLAG_LIFECYCLE_PENDING` (set via def-flag inheritance) is first written. Removed when the card's dead bit flips.
- `PlayerProfile.lifecycle_count` + `earliest_lifecycle_expires_ms` — summary fields. The hot-path block check reads only these and short-circuits when zero.

Block-check gate ([`lifecycle_pending::block_check`](src/lifecycle_pending.rs), called from `propose_action` / `add_card` / `create_character` / `deploy_mini_zone`):
- If the caller has zero active lifecycle entries, or all are within the 60-second grace window past `expires_at_ms`, the call proceeds.
- If past grace, the call is rejected unless `involved_card_ids` (built from hex/root/slots in `propose_action`) overlaps the caller's blocked rows. The permissive carve-out treats any reference to a blocked card as a resolution attempt.
- Defensive: stale rows referencing non-existent cards are purged inline before the gate evaluates.

Failure path: regular `Stack(_)` recipes whose root is the lifecycle-pending card. The recipe authoring convention requires every magnetic-style card to have an unconditionally-matchable failure recipe so a player who can't fill the success path can always resolve out. Decay-style cards (zero-slot lifecycle recipe) use the same recipe as both success and fallback — no separate failure path needed.

Client wiring lives at [pixijs/src/game/lifecycle/LifecycleResolutionManager.ts](../../../../pixijs/src/game/lifecycle/LifecycleResolutionManager.ts); see [docs/LIFECYCLE_REWRITE.md](../../../../docs/LIFECYCLE_REWRITE.md) for the design.

## Scheduled tables
SpacetimeDB scheduled tables use `#[table(accessor = ..., scheduled(<reducer_ident>))]` and require a `scheduled_at: ScheduleAt` column. Two patterns in use in this module:

- **Recurring GC sweep.** [`gc_schedule`](src/gc.rs) — single row, `ScheduleAt::Interval(10 min)`, seeded by the module's `init` reducer. Fires `gc_sweep` which walks `cards` / `players` / `souls` once each and applies player-aware retention (prior-version reap; dead-row retention bounded by login state + 30-day hard cap). Replaces the retired per-write `schedule_delete_*` model.
- **Future-stamped row, no scheduler involvement.** `action_completion::apply` writes future-stamped rows directly into `cards`. The "schedule" is implicit in the row's `valid_at_time`; the client's `ValidAtTable.promote(buffered_now)` surfaces it when wall-clock catches up. No scheduled reducer is needed. This is the pattern most actions use.

## SpacetimeDB 2.x macro syntax (migration trap)
- `#[table(name = "cards", public)]` is the **1.x** form. In 2.x it produces a confusing "method `cards` not found on `Local`" cascade because the macro fails to expand. Replace with `#[table(accessor = cards, public)]`.
- `accessor = <ident>` is required; `name = "<string>"` is an optional override for the SQL table name. The accessor doubles as the default SQL name.
- Scheduled tables: `#[table(accessor = ..., scheduled(<reducer_ident>))]`. The struct must include `scheduled_at: ScheduleAt`.
- Calling another table's accessor from a different file requires the trait in scope: `use crate::cards::cards;` — the trait is named after the accessor, not the struct. Several modules use the `as _cards_table` alias pattern to bring the trait in without shadowing the module name.
- **Non-table reducer-arg structs need `#[derive(SpacetimeType)]`.** That's how `CardStack` in [stacks.rs](src/stacks.rs) is wired — wire format, not a row.
- **`#[reducer(client_disconnected)]`** is wired to disconnect events (`players::client_disconnected`). `#[reducer(init)]` isn't used in this module; it is in [chat](../chat/AGENTS.md).
- `#[auto_inc]` only applies to the `#[primary_key]` column. When a PK moves elsewhere, the original auto-inc column becomes caller-supplied.

## Time
- `ctx.timestamp` is a `Timestamp` (microseconds since epoch).
- Every module defines a local `fn now_ms(ctx) -> u64 = (ctx.timestamp.to_micros_since_unix_epoch() / 1_000) as u64`. The u64 ms value is what fills the upper 48 bits of `valid_at` via `pack_valid_at(time_ms, sequence)`.
- To round-trip a `time_ms` back into a schedule: `ScheduleAt::Time(Timestamp::from_micros_since_unix_epoch((time_ms as i64) * 1_000))`.
- Recipe durations in JSON are seconds; convert to ms when computing `completion_ms = card.valid_at_time + duration_secs * 1_000`. Card def `lifecycle_duration_ms` is already in milliseconds.
- Comparing a `valid_at_time` (u64 ms) to a `scheduled_at` (`ScheduleAt`) requires extracting both to ms first — they're not directly comparable.

## Pitfalls
- **Don't hand-roll `valid_at`.** `cards::create` / `update_with` / `update_with_at` stamp it for you via `pack_valid_at(time_ms, sequence::next_sequence(ctx))`. The handful of callers that need a specific `time_ms` (action completions, OnCreate from a future-stamped row) use the `_at` variants, which still stamp the sequence. There's no public API that takes a pre-built `valid_at`.
- **Use `prior_at(ctx, id, time_ms)`, not `latest`, when writing past `now`.** A future-stamped product is invisible to `latest()` by definition. `on_create::trigger` exists because of this; if you're chasing "why is this lookup returning `None` for a card I just spawned?" — that's why.
- **`update_with` returns `None` if no row exists for the id.** All `set_*` helpers inherit this — they no-op when the row hasn't been created yet. Don't paper over with `unwrap_or_default`; spawn the card first via `create` / `create_at`.
- **Public vs private affects the wire.** Only `public` tables appear in generated bindings and accept client subscriptions. `player_sessions`, `sequence_counter`, `card_id_counter`, `lifecycle_pending`, and `gc_schedule` are intentionally private.
- **Bindings are generated, not edited.** Wrong types on the TS side mean a wrong Rust schema; fix Rust and rerun `bin/st build shard` (or `bin/st build` for all modules). Output lands under `pixijs/src/server/spacetime/bindings/shard/`.
- **Reducer signature for scheduled tables takes the row by value.** Changing the schedule table's shape changes the reducer's arg type — keep them in sync.
- **Don't OR holds onto a card without propagation.** If you set `position_hold_count` via the bit transform inside an open `update_with` closure, follow up with `propagate_position_hold_forward(..., delta)` so future rows reflect the same delta. Prefer the high-level `acquire_position_hold` / `release_position_hold` helpers when there's no other reason to keep the closure open.
- **`FLAG_OWNED_BY_PLAYER` is asymmetric** — set on soul cards, clear on everything else (including world-owned cards, which use `owner_id = 0` AND the bit clear). Setting it incorrectly breaks `owning_player`'s walk.
- **The build runs in a container** — paths in errors are `/workspace/server/modules/shard/...`, which maps to `spacetime/server/modules/shard/...` on the host.
- **`gen-ids.py` runs before cargo and can fail the whole build** under `set -euo pipefail`. If `bin/st build` halts before "Compiling", the content submodule is the suspect, not your Rust changes. Cross-reference [content/AGENTS.md](../../../../content/AGENTS.md) (or `git status` in `content/`) before chasing phantom Rust errors.
