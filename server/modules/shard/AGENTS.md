# AGENTS.md — shard module

## Purpose
SpacetimeDB 2.1.0 server module (Rust → wasm32). Authoritative gameplay state: the world (`cards`, `zones`), the soul mirror (`souls`), the player roster (`players`, `player_profiles`, `lifecycle_pending`), and the recipe / movement pipelines. Publishes to `resonantdust-<env>-shard` (see [`spacetime.<env>.json`](spacetime.dev.json) — `--env <env>` to switch). Compiles and runs inside a Docker-hosted SpacetimeDB instance — never against a host `spacetime` CLI.

Chat is a **separate module** ([../chat/AGENTS.md](../chat/AGENTS.md)) with its own database, queue, and wasm; nothing in this module references it.

Lifecycle-pending cards (magnetic anchors AND on_create-style decay cards) share one mechanism: a `lifecycle:` block on the card def stamps `FLAG_LIFECYCLE_PENDING` at creation via definition-flag inheritance, populates a `lifecycle_pending` detail row, and waits for the client to submit the declared recipe via `propose_action`. The dedicated `magnetic.rs` tick module is gone; the legacy `on_create.rs` module is also gone (deleted in [lifecycle rewrite](../../../../docs/LIFECYCLE_REWRITE.md) Phase 6). Pending tweaks tracked in that doc; the flag is still spelled `magnetic` (bit 2) in [`content/cards/flags.json`](../../../../content/cards/flags.json) — the rename to `lifecycle_pending` is the last Phase-1 cleanup.

## Build & iterate
- **Always** use `bin/st build shard` (or `bin/st build` to do every module). The wrapper runs [`content/gen-ids.py`](../../../../content/gen-ids.py), then `cargo build --release --target wasm32-unknown-unknown` inside the build container with workdir set to `/workspace/server/modules/shard`, then regenerates TS bindings into [`../../../../pixijs/src/server/spacetime/bindings/shard/`](../../../../pixijs/src/server/spacetime/bindings/shard/). Don't reach for `cargo`, host `spacetime`, or ad-hoc `docker compose run` — even for introspection.
- `bin/st publish shard` / `bin/st republish shard` push the wasm to the running `start` container. The CLI loads [`spacetime.json`](spacetime.json) (anchor file — empty but its existence pins the CLI in this directory) plus [`spacetime.<env>.json`](spacetime.dev.json) for db name / server. `bin/st sql shard ...`, `bin/st select shard ...`, `bin/st call shard <reducer>` for live queries. See [`bin/st`](../../../../bin/st) and [bin/AGENTS.md](../../../../bin/AGENTS.md).
- **One-shot refresh after content / schema edits: `bin/st re`** — chains `content wasm; st build shard; st delete shard; st bootstrap`. Use this when JSON catalogs change, the Zone schema changes, or you want a clean slate. `bin/st re all` rebuilds every module; `bin/st re <module>` scopes to one.
- TS bindings are generated; private tables (no `public`) are skipped during codegen. `player_sessions`, `sequence_counter`, `card_id_counter`, `lifecycle_pending`, and `gc_schedule` are intentionally private.

## The `valid_at` pattern
`cards`, `zones`, `players`, and `souls` share one primary-key shape (chat's `chat_messages` uses the same shape independently in its own module):

```
valid_at: u64 = (time_ms: u48 << 16) | sequence: u16
```

- **`valid_at` is the primary key**; the row's logical id (`card_id` / `zone_id` / `player_id`, etc.) is a `#[index(btree)]` column on the row. Two rows for the same id form a *history* of versions ordered by `valid_at_time`.
- **Time is milliseconds**, not seconds. Every module uses a local `fn now_ms(ctx) -> u64` that converts `ctx.timestamp.to_micros_since_unix_epoch() / 1_000`. The u48 ms slot has ~8920 years of runway.
- **The sequence is the source of PK uniqueness across writes at the same millisecond.** [`sequence::next_sequence(ctx)`](src/sequence.rs) hands out a fresh `u16` per call. Without it, two writes to different cards landing in the same ms would collide; with it, the only collision case is "same id, same `time_ms`."
- **Same-(id, time_ms) writes** are explicitly purged before insert. `cards::write_at` calls `delete_at(ctx, card_id, time_ms)` so "last write at this (id, ms) wins" — without the purge, the global sequence would let two rows for the same card share a time_ms, breaking in-reducer accumulation patterns (e.g. `souls::apply_slot_delta` firing N times at one `now_ms`, which is exactly what `bootstrap`'s starter-pack add-loop does).
- **Future-stamped rows are first-class.** Recipe completions and movement step queues are stamped at a `valid_at_time > now`. `latest()` therefore filters `valid_at_time ≤ now_ms` (max-by-key among those) — it does NOT just take the deepest row. `cards::prior_at(ctx, card_id, time_ms)` is the parameterised form used by writers that want "the row current at the time we're writing." Zones (`set_tile_at`) and souls (`apply_slot_delta`) use the same discipline.
- **`latest()` and `prior_at()` are not interchangeable.** A caller that has stamped a future row should reach the new state via `prior_at(..., future_time)`, never `latest()`. Recipe products spawned by `action_completion::apply` at `completion_ms` exist *only* at that future stamp — readers wanting to consult their state must pass that `time_ms` explicitly to `prior_at`.
- **No `#[unique]` on non-PK columns.** Cross-row uniqueness (e.g. unique player names) can't be enforced via `#[unique]` — every version row would collide. Use `#[index(btree)]` and check via `latest_by_*()` lookup in the reducer before insert. Reducers are serialized per-database, so lookup-then-insert is race-free.
- **`#[auto_inc]` only on the PK.** When the PK moved to `valid_at`, the original id columns became caller-supplied. Cards now get ids from `cards::next_card_id` (private `card_id_counter` single-row table — *not* `content/gen-ids.py`, which only allocates `def_id`s for the catalog); zones via `zones::next_zone_id`; players via `players::next_player_id` (scan-and-increment fallback).

Client mirror: [pixijs/src/server/data/packing.ts](../../../../pixijs/src/server/data/packing.ts) and [pixijs/src/server/data/ValidAtTable.ts](../../../../pixijs/src/server/data/ValidAtTable.ts). Same packed-key shape, same "select max `valid_at_time` ≤ buffered_now per id" semantics. Schema changes here ripple through bindings and require updates over there.

## The `flags` columns
`Card` carries **two** flag hosts, both `u32`: `flags_state` (state bits — what is true about the card; forward-propagated by `propagate_flag_diff_forward` in `cards::write_at`) and `flags_bk` (bookkeeping — refcount holds + dirty/preserve markers + tile-card stock; never bit-diff propagated). Bit positions are pinned by [`content/cards/flags.json`](../../../../content/cards/flags.json) — the file's `_comment` blocks are the canonical reference. Helpers in [`cards.rs`](src/cards.rs) provide the typed accessors; **read flag values via the field-routing helpers from the content crate**, not hardcoded shifts, so renumbering doesn't fan out.

**`flags_state` (state bits):**

| Bits | Name | Notes |
| --- | --- | --- |
| 0 | `dead` | Server marked the card consumed. Set via UPDATE so the row carries a death `valid_at` the client can time its dying animation against. |
| 1 | `force_position` | "Server asserts this row's `micro_zone` / `micro_location` verbatim — client overwrites local guesses." Set on chain-stitch writes; cleared at completion. |
| 2 | `magnetic` | Lifecycle-pending marker. Stamped at creation for any def with a `lifecycle:` block via definition-flag inheritance. Cleared when the resolving recipe completes. Name kept as `magnetic` for stable-id discipline pending the lifecycle Phase-1 rename. |
| 3 | `surface_locked` | Static — card may not change surface. |
| 4 | `is_owned_by_player` | Disambiguates `Card.owner_id`. SET → `owner_id` is a `player_id` (soul cards). CLEAR → `owner_id` is a `card_id` (container; `0` = world). [`cards::owning_player`](src/cards.rs) walks until it hits this bit. |
| 5..=7 | `progress_style` (u3) | Progress-bar style for the row's "next future event" client render. 0 = none, 1 = LTR/CW, 2 = RTL/CCW. |
| 8..=11 | `portrait_id` (u4) | Soul-card portrait selector. |

**`flags_bk` (bookkeeping):**

| Bits | Name | Notes |
| --- | --- | --- |
| 0 | `position_dirty` | Auto-set when the new row's position fields differ from prev. Server-managed, do not write manually. |
| 1 | `position_preserve` | Caller intent: future-prop must not overwrite this row's position. Movement scrub stops at the first row carrying it. |
| 2 | `data_dirty` | Auto-set when `flags_state`/`owner_id`/`packed_definition` differ from prev. Server-managed. |
| 3 | `data_preserve` | Caller intent: future-prop must not overwrite this row's data. `propagate_flag_diff_forward` skips it. |
| 4..=6 | `position_hold_count` (u3) | Refcount; `> 0` means position-pinned. Absorbs the retired `position_locked` single-bit via the "lock = never-released +1" idiom. |
| 7..=9 | `slot_share_count` (u3) | Refcount of shared (`borrow.` / `share.`) holds. |
| 10..=12 | `drop_hold_count` (u3) | Refcount; `> 0` blocks stacking onto this card as a child. Absorbs the retired `drop_locked` bit. |
| 13..=15 | `slot_hold_count` (u3) | Refcount of exclusive (`claim.` / `use.`) holds. Absorbs the retired `slot_hold` single bit. |
| 16..=17 | `touch_count` (u2, max 3) | Cap of client-initiated recipes touching this card concurrently. `validate_bindings` rejects a 4th. |
| 18..=19 | `server_count` (u2, max 3) | Cap of server-internal touches. Same shape as `touch_count`, separate field so server activity can't starve clients. |
| 20..=21 | `tile_stock_0` (u2) | Stock slot 0 for promoted tile-cards. Seeded from the Zone on `find_or_create_tile_card`, written by `Effect::ModifyTileStock`, folded back to the Zone on GC demotion. |
| 22..=23 | `tile_stock_1` (u2) | Sibling of `tile_stock_0` for slot 1. |

**Helpers.** Acquire / release / propagate triplets exist for each refcount in `flags_bk` via the `decl_count_ctx!` macro in [`cards.rs`](src/cards.rs) — `acquire_<name>` / `release_<name>` / `propagate_<name>_forward`. Use these (or the high-level `acquire_position_hold`, `acquire_slot_hold`, etc.) rather than hand-rolling field arithmetic; they own the forward-propagation discipline so overlapping holders compose correctly across future-stamped completion rows.

Permanent locks are expressed as `acquire_<name>` at spawn with no matching release — the `+1` floor keeps `count > 0` forever, and the gate "is this card held?" stays a single `count > 0` check.

Definition-level flags inherit on `create` / `create_at` — see `definition_flag_mask` in [cards.rs](src/cards.rs). Don't OR them by hand at every call site.

**Client-side drag holds** live in a `DragHoldStore` sidecar inside `pixijs/src/game/input/DragManager.ts` — the server has no concept of an in-flight client drag, so drop-target gates consult both `drop_hold_count > 0` (server-side) and `DragHoldStore.has(targetId)` (client-only).

## Surface bands
`Card.surface` and `Zone.surface` are `u8`, but the values are banded into ranges with different semantics. The constants live in [packed.rs](src/packed.rs):

| Band | Constant | Purpose |
| --- | --- | --- |
| `0` | (reserved) | Sentinel "absent." Don't write here. |
| `1` | `INVENTORY_LAYER` | A soul's inventory bucket. `macro_zone = soul.card_id`. No hex tile data. |
| `2` | `PLAYER_INVENTORY_LAYER` | A player's account-wide inventory bucket, shared across all of that player's souls (for permanent / account-scoped items). Same bucket convention as soul inventory but `macro_zone = player_id`. No hex tile data. |
| `3..32` | (reserved) | Future personal / panel surfaces. |
| `32` | `POCKET_DIMENSION_LAYER` | Card-anchored pocket dimension. `macro_zone = anchor.card_id`. Reserved — no reducer creates these yet. |
| `33..62` | (reserved) | Future tile-bearing surfaces. |
| `62` | `PLAYER_DIMENSION_LAYER` | A player's private 2×2 grid of `Zone`s — where all their souls live and permanent state accumulates. **Unique convention:** `macro_zone = pack(chunk_q, chunk_r)` (same as world), and **multiple players' Zones coexist at the same `macro_zone`** — `Zone.owner_id == player_id` is the discriminator. Lookups MUST use `zones::latest_for_owner` (owner-aware) instead of `latest_for`; tile-read helpers in `cards.rs` take an `Option<u32> owner_id_filter` arg threaded from the calling reducer's `caller_player_id`. Eager-created in `claim_or_login`'s new-player branch via `zones::create_player_dimension`. See [src/player_dimension.rs](src/player_dimension.rs). |
| `63` | `MINI_ZONE_LAYER` | Mini_zones — radius-3 hex disks overlaid on the world. `macro_zone = anchor.card_id`. Backed by a real `Zone` row; cards placed on the mini_zone follow the same address. |
| `64..` | `WORLD_LAYER = 64` | World tiles. `macro_zone = packed (zone_q, zone_r)`. Synthetic hexes come from the underlying `Zone.tile_row`; if a mini_zone covers the same hex, it occludes. |

`actions.rs` and `action_completion.rs` both define `WORLD_LAYER = 64` locally — they MUST agree. The split between "carries tile data" (`>= 32`) and "panel / inventory" (`< 32`) is also the gating for synthetic-hex derivation.

**Owner discrimination on surface 62.** Every tile-read helper that touches a Zone (`cards::tile_def_id_view`, `tile_full_view`, `find_tile_card_at`, `find_or_create_tile_card`, `inspect_hex`) and `derive_synthetic_hex` / `movement::tile_def_at` take `owner_id_filter: Option<u32>`. Pass `Some(player_id)` on `PLAYER_DIMENSION_LAYER` and `None` on every other surface. The filter scopes both the Zone resolution (`latest_for_owner` vs `latest_for`) and the card-iteration `macro_zone` scan inside `inspect_hex`.

## Stacks: chains and the wire format
`micro_zone: u8` has **two interpretations**, gated by `(stacked_state, surface)`:

- **Stack layout** — `stacked_state == OnRoot` AND `surface < 64`: `[position: u4 | direction: u2 | stacked_state: u2]`. The card's position in the chain (1..=15; saturates at 15 — deeper chains are rejected at propose-time) and its direction off the root: **`0 = HEX` (tile / branch 0)**, **`1 = UP` (top / branch 1)**, **`2 = DOWN` (bottom / branch 2)**. Direction byte value matches recipe branch number — `chain_stitch` writes `direction = iterator.branch`. Value 3 reserved.
- **Free / loose layout** — every other case (`Free` / `Slot` / world cards): `[q: u3 | r: u3 | stacked_state: u2]`. Local (q, r) within the macro zone.

`StackedState` (3 active variants + 1 reserved) lives in [content/src/packed.rs](../../../../content/src/packed.rs); the shard module re-exports via `pub use resonantdust_content::packed::*;`:

- **`Free` (0)** — Loose. `micro_location` is encoded `(x, y)` for surface-local positioning; `micro_zone` upper 6 bits are the (q, r) bits. World cards / inventory loose cards / tile-cards all live here.
- **`Slot` (1)** — Parent-pointer slot. `micro_location` is the **immediate parent's** `card_id`. Used during recipe binding for the in-flight "this card is part of an action's structure" linkage; chain_stitch writes `Slot` for non-leaf members.
- **`OnRoot` (2)** — Stacked on a rect chain root. `micro_location` is the **root's** `card_id` (not the immediate parent). Chain order comes from `micro_zone.position`; branch (HEX/UP/DOWN) from `micro_zone.direction`. Produced by `propose_action`'s chain_stitch and by `place_card`'s `PLACEMENT_STACK` path.
- **Value 3** — Reserved. Was `OnHex` under the legacy hex-anchored model; that case is gone under the unified-card / tile-as-card model (a hex card stacked under a rect is `OnRoot` with `direction = HEX`, not a third state). `StackedState::from_u2(3)` panics — never write this value.

Hex / tile cards are *just* cards: a loose tile-card is `Free` at the world surface with `(q, r)` in `micro_zone`; a tile-card bound to a recipe ends up `OnRoot` with `direction = HEX` under the chain root. **`chain_stitch` rewrites a recipe-bound tile-card's `micro_zone` from the Free `(q, r)` layout to the OnRoot stack layout** — readers that need the tile-card's hex must parent-walk to its Free ancestor (see `cards::tile_full_view`'s implementation and the matching `LayoutWorld.resolveTileCardHex` on the client).

The wire-format `CardStack` struct in [stacks.rs](src/stacks.rs) is a reducer-arg shape (`#[derive(SpacetimeType)]`, not a `#[table]`). `submit_action` (the original consumer) is commented out, so `apply` is only reachable through internal callers today.

`unpack_micro_zone(micro_zone) -> (q, r, state)` and `pack_stack_micro_zone(position, direction, state)` / `pack_slot_micro_zone(direction)` / `pack_micro_zone(q, r, state)` switch between the two interpretations. Use the right packer for the state you're writing.

## Action pipeline
Recipe execution under the [recipe-tape model](../../../../docs/RECIPE_TAPE_REWRITE.md). Two reducers, no `OnCreate` trigger module (deleted in the lifecycle rewrite):

1. **Propose.** Client matches the recipe locally and submits `propose_action(client_time_ms, recipe_id, surface, macro_zone, micro_zone, root, bindings: Vec<Vec<u32>>)`. The server resolves `effective_now_ms(client_time_ms)?` once and threads `now_ms` everywhere. The propose path runs in stages:
   - **Stage 1 (input verify).** Walk `recipe.input`, resolve each `Seg::Slot { iter, offset }` via `bindings[iter][offset]`, evaluate predicates. `.owner` / `.parent` transition steps verify against the previously-resolved card's `owner_id` / `micro_location`. Branch 0 supports a synthetic-tile sentinel (`bindings[iter_0][0] == 0` → derive from zone tile); if it fires, the tile is promoted to a real card via `cards::find_or_create_tile_card` and the binding is substituted before any downstream stage sees it.
   - **Stage 2 (existence / liveness).** Every `card_id` in bindings exists, alive, ownership chains back to caller (`is_owned_by_player` walk), no foreign in-flight slot_hold.
   - **Stage 3 (chain-stitch).** Root lands `Free` at `(surface, macro_zone, micro_zone)`; top-level iterator bindings (parent path empty) are stitched into branch `iterator.branch` as parent-pointer chains. Nested-iterator bindings (parent path non-empty) are left alone — their cards already live in other chains (e.g., the axe in the player's equipment for cut_tree).
   - **Stage 4 (lock + schedule).** `acquire_touch` per card per recipe; `acquire_slot_hold` / `acquire_slot_share` / `acquire_position_hold` per binding kind. `lifecycle_pending::block_check` runs (permissive carve-out for resolution attempts). `action_completion::apply` is invoked with `completion_ms = now_ms + duration_secs * 1000`.
2. **Apply.** [`action_completion::apply`](src/action_completion.rs) walks the recipe's output tape sequentially. Tape state: `vars: [i32; 8]`, `duration`, `style`, `pending: Vec<Effect>`. Output ops: `sys.duration.set`, `sys.style.set`, `var.N.set/add/sub` (Int literal or path RHS via `read_path_value`), `when.<var-pred>.<inner>` gates, `<path>.destroy`, `<path>.create: <def_id>`, `<path>.aspect.X.sub/add/set`. After the walk, all `Effect`s are emitted as future-stamped rows at `completion_ms`: reagent rows flip `FLAG_DEAD`, products spawn via `cards::create_at`, tile-stock writes target the promoted tile-card's `flags_bk` via `cards::set_tile_stock`. Then `release_touch` / `release_slot_hold` / `release_slot_share` / `release_position_hold` per binding.

Lifecycle-pending cards consumed during apply have their `lifecycle_pending` row removed by the dead-transition hook in `cards::write_at`.

The `actions` flow has no server-side action table — its state is the cards it stamped. The `lifecycle_pending` table tracks ACTIVE lifecycle-pending cards (one row per lifecycle-flagged card); see the next section.

## Lifecycle resolution gate
Lifecycle-pending cards (magnetic anchors today; on_create-style decay cards under the [lifecycle rewrite](../../../../docs/LIFECYCLE_REWRITE.md)) are recipes with a time-windowed phase. Resolution is **client-driven** — the server stamps initial state, the client decides when to submit success / failure / decay recipes via `propose_action`.

State on the server:
- [`lifecycle_pending`](src/lifecycle_pending.rs) — private table, one row per active lifecycle entry. Populated by `cards::write_at` when a card carrying `FLAG_LIFECYCLE_PENDING` (set via def-flag inheritance) is first written. Removed when the card's dead bit flips.
- `PlayerProfile.lifecycle_count` + `earliest_lifecycle_expires_ms` — summary fields. The hot-path block check reads only these and short-circuits when zero.

Block-check gate ([`lifecycle_pending::block_check`](src/lifecycle_pending.rs), called from `propose_action` / `add_card` / `create_character` / `deploy_mini_zone`):
- If the caller has zero active lifecycle entries, or all are within the 60-second grace window past `expires_at_ms`, the call proceeds.
- If past grace, the call is rejected unless `involved_card_ids` (built from hex/root/slots in `propose_action`) overlaps the caller's blocked rows. The permissive carve-out treats any reference to a blocked card as a resolution attempt.
- Defensive: stale rows referencing non-existent cards are purged inline before the gate evaluates.

Failure path: regular `Stack(_)` recipes whose root is the lifecycle-pending card. The recipe authoring convention requires every magnetic-style card to have an unconditionally-matchable failure recipe so a player who can't fill the success path can always resolve out. Decay-style cards (zero-slot lifecycle recipe) use the same recipe as both success and fallback — no separate failure path needed.

Client wiring lives at [pixijs/src/game/lifecycle/LifecycleResolutionManager.ts](../../../../pixijs/src/game/lifecycle/LifecycleResolutionManager.ts); see [docs/LIFECYCLE_REWRITE.md](../../../../docs/LIFECYCLE_REWRITE.md) for the design.

## Scheduled tables
SpacetimeDB scheduled tables use `#[table(accessor = ..., scheduled(<reducer_ident>))]` and require a `scheduled_at: ScheduleAt` column. Two patterns in use in this module:

- **Recurring GC sweep.** [`gc_schedule`](src/gc.rs) — single row, `ScheduleAt::Interval(10 min)`, seeded by the module's `init` reducer. Fires `gc_sweep` which walks `cards` / `players` / `souls` once each and applies player-aware retention (prior-version reap; dead-row retention bounded by login state + 30-day hard cap). Replaces the retired per-write `schedule_delete_*` model.
- **Future-stamped row, no scheduler involvement.** `action_completion::apply` writes future-stamped rows directly into `cards`. The "schedule" is implicit in the row's `valid_at_time`; the client's `ValidAtTable.promote(buffered_now)` surfaces it when wall-clock catches up. No scheduled reducer is needed. This is the pattern most actions use.

## SpacetimeDB 2.x macro syntax (migration trap)
- `#[table(name = "cards", public)]` is the **1.x** form. In 2.x it produces a confusing "method `cards` not found on `Local`" cascade because the macro fails to expand. Replace with `#[table(accessor = cards, public)]`.
- `accessor = <ident>` is required; `name = "<string>"` is an optional override for the SQL table name. The accessor doubles as the default SQL name.
- Scheduled tables: `#[table(accessor = ..., scheduled(<reducer_ident>))]`. The struct must include `scheduled_at: ScheduleAt`.
- Calling another table's accessor from a different file requires the trait in scope: `use crate::cards::cards;` — the trait is named after the accessor, not the struct. Several modules use the `as _cards_table` alias pattern to bring the trait in without shadowing the module name.
- **Non-table reducer-arg structs need `#[derive(SpacetimeType)]`.** That's how `CardStack` in [stacks.rs](src/stacks.rs) is wired — wire format, not a row.
- **`#[reducer(client_disconnected)]`** is wired to disconnect events (`players::client_disconnected`). `#[reducer(init)]` isn't used in this module; it is in [chat](../chat/AGENTS.md).
- `#[auto_inc]` only applies to the `#[primary_key]` column. When a PK moves elsewhere, the original auto-inc column becomes caller-supplied.

## Time
- `ctx.timestamp` is a `Timestamp` (microseconds since epoch).
- Every module defines a local `fn now_ms(ctx) -> u64 = (ctx.timestamp.to_micros_since_unix_epoch() / 1_000) as u64`. The u64 ms value is what fills the upper 48 bits of `valid_at` via `pack_valid_at(time_ms, sequence)`.
- To round-trip a `time_ms` back into a schedule: `ScheduleAt::Time(Timestamp::from_micros_since_unix_epoch((time_ms as i64) * 1_000))`.
- Recipe durations in JSON are seconds; convert to ms when computing `completion_ms = card.valid_at_time + duration_secs * 1_000`. Card def `lifecycle_duration_ms` is already in milliseconds.
- Comparing a `valid_at_time` (u64 ms) to a `scheduled_at` (`ScheduleAt`) requires extracting both to ms first — they're not directly comparable.

## Time discipline (`client_time_ms` + grace)
Every public state-writing reducer takes `client_time_ms: u64` as its first arg after `ctx`. The client submits its `serverNowMs()` estimate; the server validates and uses the result for *all* in-reducer time reads.

- **[`cards::effective_now_ms(ctx, client_time_ms)`](src/cards.rs)** is the single helper every reducer calls. Returns `min(client, server)` if within grace, or `Err("time_drift:client_(behind|ahead)_by=<N>")` if not. The asymmetric grace policy: back-grace `TIME_DRIFT_BUFFER_MS + MAX_RTT_MS` (= 5000 ms), forward-grace `TIME_DRIFT_BUFFER_MS` (= 2000 ms). The client's [`ActionManager`](../../../../pixijs/src/game/actions/ActionManager.ts) parses the `time_drift:client_ahead_by=<N>` form and retries after `N + 250 ms`.
- **Why two grace windows.** SpacetimeDB stamps history rows with `valid_at` and the client gates rows into its current view at a buffered `serverNowMs()`. If the client claims a `time_ms` ahead of the server, the resulting row is invisible until wall-clock catches up — visible as ghost rejections. If the client claims behind, the row is already past — visible as race conditions against follow-up reducers. The grace absorbs RTT (back-direction) while staying tight enough on the forward direction to keep rejections diagnosable.
- **`*_at(time_ms)` variants** on `cards.rs`, `players.rs`, and `zones.rs` (`create_at`, `update_with_at`, `write_at`) stamp the row's `valid_at` at an explicit `time_ms` instead of `now_ms(ctx)`. Every reducer that's resolved an `effective_now_ms` value uses the `_at` form so the row's stamp matches what the client expects to see.
- **Grace-exempt reducers.** `claim_or_login` and `set_last_login` bootstrap / reseed the client's offset window — they can't depend on the client having a valid offset yet. Both accept `_client_time_ms: u64` and ignore it. Both back-shift their row writes by `TIME_DRIFT_BUFFER_MS` so the player row's `valid_at` matches the buffered `serverNowMs()` the client will read *as soon as the capture seeds the window* (otherwise login waits 2 s for promote-gating).
- **Grace-applying reducers.** `propose_action`, `place_card`, `move_soul`, `create_character`, `add_card`, `deploy_mini_zone`, `pickup_mini_zone`, `enter_player_dimension`, `exit_player_dimension`, `request_blueprint`, `request_player_blueprint`. Each resolves `let now_ms = cards::effective_now_ms(ctx, client_time_ms)?;` at the top and threads `now_ms` through every downstream helper (`chain_stitch`, `validate_bindings`, `apply_locks`, `action_completion::apply`, `lifecycle_pending::block_check`, `cards::prior_at`, `cards::update_with_at`).
- **Admin / scheduled reducers** (`bootstrap`, `generate_forest_terrain`, `gc_sweep`) don't take `client_time_ms` — they're not user-driven game actions. They use raw `now_ms(ctx)` directly.

Client-side counterpart: [pixijs/src/server/spacetime/ReducerManager.ts](../../../../pixijs/src/server/spacetime/ReducerManager.ts) owns the `serverNowMs()` estimator (16-sample rolling window over `Reducer`-tagged callbacks, `performance.now()` as the monotonic anchor, `Date.now()` as the freshness selector).

**Pitfalls when adding a new reducer:**
- If it writes game state: route everything through `effective_now_ms` and `_at` variants. Don't sprinkle raw `now_ms(ctx)` calls inside the reducer body — they'd race against the resolved `now_ms` and stamp rows the client can't promote on schedule.
- The `client_time_ms` arg must come **first** (after `ctx`), so the client wrapper's positional injection works uniformly across reducers.
- If it's an admin / debug entry point not meant for end-user clients, leave it on `now_ms(ctx)` and document the exemption (same shape as `bootstrap`).

## Pitfalls
- **Don't hand-roll `valid_at`.** `cards::create` / `update_with` / `update_with_at` stamp it for you via `pack_valid_at(time_ms, sequence::next_sequence(ctx))`. The handful of callers that need a specific `time_ms` (action completions, OnCreate from a future-stamped row) use the `_at` variants, which still stamp the sequence. There's no public API that takes a pre-built `valid_at`.
- **Use `prior_at(ctx, id, time_ms)`, not `latest`, when writing past `now`.** A future-stamped product is invisible to `latest()` by definition. If you're chasing "why is this lookup returning `None` for a card I just spawned?" — that's why; the product row's `valid_at_time` is `completion_ms`, not `now`.
- **`update_with` returns `None` if no row exists for the id.** All `set_*` helpers inherit this — they no-op when the row hasn't been created yet. Don't paper over with `unwrap_or_default`; spawn the card first via `create` / `create_at`.
- **Public vs private affects the wire.** Only `public` tables appear in generated bindings and accept client subscriptions. `player_sessions`, `sequence_counter`, `card_id_counter`, `lifecycle_pending`, and `gc_schedule` are intentionally private.
- **Bindings are generated, not edited.** Wrong types on the TS side mean a wrong Rust schema; fix Rust and rerun `bin/st build shard` (or `bin/st build` for all modules). Output lands under `pixijs/src/server/spacetime/bindings/shard/`.
- **Reducer signature for scheduled tables takes the row by value.** Changing the schedule table's shape changes the reducer's arg type — keep them in sync.
- **Don't OR holds onto a card without propagation.** If you set `position_hold_count` via the bit transform inside an open `update_with` closure, follow up with `propagate_position_hold_forward(..., delta)` so future rows reflect the same delta. Prefer the high-level `acquire_position_hold` / `release_position_hold` helpers when there's no other reason to keep the closure open.
- **`FLAG_OWNED_BY_PLAYER` is asymmetric** — set on soul cards, clear on everything else (including world-owned cards, which use `owner_id = 0` AND the bit clear). Setting it incorrectly breaks `owning_player`'s walk.
- **The build runs in a container** — paths in errors are `/workspace/server/modules/shard/...`, which maps to `spacetime/server/modules/shard/...` on the host.
- **`gen-ids.py` runs before cargo and can fail the whole build** under `set -euo pipefail`. If `bin/st build` halts before "Compiling", the content submodule is the suspect, not your Rust changes. Cross-reference [content/AGENTS.md](../../../../content/AGENTS.md) (or `git status` in `content/`) before chasing phantom Rust errors.
